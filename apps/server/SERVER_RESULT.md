## Round 3 (2026-10-04): bot tricks + reconnect races

**Bot tricks.** Bots issued only accusations in the browser e2e. Changes in `src/bot.ts`: trick attempt chance per decision 5% → 22%, shopping 55% → 70% with wallet ≥300. Bot loop extracted from `Room` into exported `runBots(engine, mem, now, rnd, wrap)` so it can be tested without sockets. New `test/bots.test.ts` (virtual clock, 4 bots, 12 hands): 63 accepted trick commands (T01 30, T02 10, F01 11, F02 12; 13 gear buys) ≈ 5/hand across the table; asserts ≥0.4 tricks/hand, free fakes, buy→equip and real tricks occur. Bots still never use T03/F03/T05–T07 or contracts.

**Reconnect races (found with a new stress test, both real).**
1. *Reservation pile-up locks the room.* Each abrupt drop leaves a Colyseus `allowReconnection` reservation (45 s) that counts toward `maxClients`; after ~14 quick refreshes the room reported `locked` and `joinById` failed ("room is locked"). Likely cause of "refresh didn't resume". Fix: Room `maxClients = 4×4` (real table size is already enforced in `onAuth`/`addBot`), and on a successful `rejoinKey` claim the stale session is *superseded*: its seat is removed, its pending reservation is rejected (via Colyseus internal `_reconnections` — private API, wrapped in try/catch, re-check on Colyseus upgrade) and its socket closed.
2. *Old connection's drop/leave arriving after rejoin.* Previously `findClaim` required the old seat to be gone, so a rejoin during the old socket's reservation was refused (Ván đã bắt đầu…) until it expired, and a late `onLeave` could `setConnected(false)` or, in lobby/finished, `removePlayer` the freshly rejoined player. Now a valid `rejoinKey` takes the seat immediately, and `onDrop`/`onLeave` are no-ops when a newer session owns the player.
- Stress test (`integration.test.ts`): 50 abrupt close + immediate `rejoinKey` join cycles, in lobby and mid-game, then asserts same playerId each time, room not locked, ≤2 live reservations, 2 players, still `connected`. Passes; full suite 101/101 twice in a row.

Caveats: this is a localhost simulation of an abrupt close; real browser/proxy close semantics and the old "refresh failed 1 in 6" were not reproduced directly, so the link to those failures is inferred, not proven. Token-based `reconnect(token)` path unchanged. Anyone holding a rejoinKey can evict the live session (by design; the key is the credential).

## Regression: refresh reconnect failing in the browser e2e (2026-10-04) — root cause + fix
**Symptoms (web console after reload):** `Room has not been up for long enough for automatic reconnection (min uptime 5000ms)`, `reconnect attempt failed … reconnection token invalid or expired` (HTTP **524**), `Room connection was closed unexpectedly (4002)` / `4003`.
**What close code 4002 is:** Colyseus `CloseCode.WITH_ERROR`. It is sent when (a) a join/reconnect handshake throws, or (b) `checkReconnectionToken` finds a *still-connected* client with that reconnection token and force-closes it (stale-socket takeover). 4003 = `FAILED_TO_RECONNECT`, 4000 = consented leave (client `leave()`), 1006 = socket died abnormally.
**Root cause (server side, reproduced with server tracing + Playwright request log):** after a refresh the new tab reconnects in ~2 s, but the browser is CPU-starved for 15–30 s while the heavy 3D page boots (swiftshader, other agents' processes). The server's ping settings (`pingInterval 5 s × pingMaxRetries 3 = 15 s`) then declared the *freshly reconnected* socket dead (`drop … code=1006`). At that moment Colyseus still holds the client in its JOINING state (the client's join ack is delayed by the same stall), and `allowReconnection()` rejects with "not joined" for such a client, so my `onDrop` fell straight through to `onLeave`: seat released, Colyseus reconnection token destroyed (hence 524 on the next `reconnect(token)`), and — in lobby/finished — the player removed outright. The web's recovery loop (30 s `withTimeout`, late-room `leave()`, retries with the new token that Colyseus treats as a live-client takeover → 4002) then cascaded. Not caused by the Round-4 phase changes, `lookDown`, `nextHand`, or `maxClients×4` (verified: those paths don't dispose or close sockets; the room only closes sockets through the paths above). I could not rule out additional browser-side slowness: in one traced run the browser's `POST /matchmake/reconnect` itself took ~69 s to complete with no server activity (client-side stall).
**Fixes (apps/server):**
1. Ping tolerance `pingInterval 8 s × 5 retries = 40 s` (`config.pingIntervalMs/pingMaxRetries`) so a starved browser isn't killed mid-handshake. Dead sockets are detected later, which is fine because a valid `rejoinKey` now takes the seat over immediately (Round 3).
2. Lobby/finished: a **non-consented** leave (any code except 4000) no longer deletes the player. The seat stays (marked disconnected) for the 45 s reconnect window and `rejoinKey` still claims it; only a consented leave (4000) or window expiry removes it. Timers are cleared on reclaim/dispose.
3. Diagnostics: always-on one-line logs for `join/drop/reconnect/leave` (session, close code, claim), and `HTTP_LOG=1` logs every HTTP request with duration.
**Tests:** stress test now runs 50 abrupt-close + `rejoinKey` cycles in **lobby, opening shop, playing and market** (room not locked, ≤2 live reservations, still connected, phase unchanged); new test for non-consented lobby socket death keeping the seat vs consented leave removing it. `npm test` all green.
**Not verified:** a clean, uncontended browser e2e pass after the fix — the machine was heavily loaded/suspended during my runs (wall-clock jumps of ~17 min), so e2e timing results are unreliable; see the final run note below if present.
